League of Legends Calculator · Internal Architecture

How the fight calculator works

A damage model for a game that is rebalanced every two weeks. The whole shape of this codebase follows from one decision: numbers live in data, structure lives in code. Riot moves the numbers; we re-pull and ship.

173 champions cached 324 items 31 champion modules 1,679 tests
01

The problem the shape solves

A fight calculator has to answer one question: if this champion, at this level, with these items, fights this target for this long — how much damage lands? That is a an arithmetic problem, and arithmetic is the easy part. The hard part is that every input to it is a moving target. Riot ships a balance patch roughly every two weeks; each one nudges base damages, AP ratios, cooldowns, item prices, and occasionally reworks a kit outright.

A calculator that hardcodes ahri_q_damage = 35 + 0.5 * ap is correct for about ten days. So no number that Riot controls is ever written in our source. Champion and item values are scraped from the League Wiki into a JSON cache; the code refers to them by name — "Damage Per Pass", not 35 — and reads whatever the current patch put in that slot.

Everything below is downstream of that. The pipeline exists to keep the scrape isolated, the champion layer exists to describe kit structure without owning kit values, and the gates exist to catch the day the trick stops working.

02

The pipeline

Data flows one direction, and two chokepoints are enforced by convention and tested for: exactly one module makes network calls, and exactly one module reads the cache.

League Wiki via vendor/lolstaticdata — external scraper, vendored, not ours to refactor external
scrape (patch day only)
data_updater.py The only module in the codebase that touches the network. Fetches, normalizes, writes the cache. writes
data/champions.json · data/items.json Patch-stamped cache, committed to git. Because it is tracked, HEAD is the previous patch — that is what makes the patch-day diff possible. cache
data_fetcher.py The only read path. No network, ever. Parsed JSON is memoized by path + mtime, so an optimizer sweep reuses one in-memory copy and still notices an update. reads

Why the chokepoints matter

One network module means the calculator is fully deterministic and offline at runtime — tests, the optimizer's thousands of build evaluations, and production all read the same frozen snapshot. One read module means a data-shape change has exactly one place to be absorbed.

03

Patch day: Riot buffs Ahri Q by 20

Take the concrete case. Ahri's Q, Orb of Deception, currently deals 35 / 60 / 85 / 110 / 135 (+50% AP) per pass. Suppose the next patch adds 20 flat damage at every rank. Here is the full trace of what happens in this codebase.

What the cache holds today

data/champions.json → Ahri.abilities.Q[0]
"leveling": [ { "attribute": "Damage Per Pass", "modifiers": [ { "values": [35, 60, 85, 110, 135], "units": ["", "", "", "", ""] }, { "values": [50, 50, 50, 50, 50], "units": ["% AP", …] } ] } ]

The five-element array is the five ability ranks; the second modifier is the AP ratio. This shape — effects[].leveling[].modifiers[].values[rank-1] — is universal across every champion in the cache, and slotlib.sum_modifiers() is the single function that walks it. Flat units add directly; unit strings like "% AP" route through scaling.resolve_scaling() against the build's live stats.

What our Ahri module says

src/calculator/champions/ahri.py
SLOTS = { "Q": simple_damage(attr="Damage Per Pass", dmg_type="mixed", casts=2), "W": _fox_fire, "E": simple_damage(dmg_type="magic"), "R": _spirit_rush, }

That single line is the entire model of Ahri's Q, and it contains no damage number. It says three structural things — read the attribute called Damage Per Pass; the orb passes through twice, so casts=2; the two passes are magic outbound and true on the return, which is what dmg_type="mixed" encodes (an even split into a magic DamagePart and a true one, mitigated separately). All three remain true after a damage buff.

What a patch does cost code

The failure this design defends against

Values are read strictly: a missing key raises, naming the item and the key. No call site is allowed a .get(key, stale_literal) fallback, because a fallback turns a loud parser break into a silently wrong number — that exact pattern once hid a 3× overstatement of Statikk Shiv's damage for weeks. Loud beats plausible.

04

The fight engine

damage.py is the simulation, and it knows nothing about any specific champion. It consumes two typed inputs — compiled item effects and champion DamageParts — and never branches on a champion or item name. Its top-level function reads as the fight model itself:

damage.py → calculate_fight_damage()
state = _resolve_combat_state(...) # resists, pen, amps, attack timing _apply_stat_buff_ultimates(state) # R steroids land before damage reads stats rotation = _compute_ability_rotation(state) _add_stacking_dot_damage(state) autos = _simulate_auto_attacks(state) # per-auto crit simulation on_hits = _layer_on_hit_effects(state, autos, rotation) spellblade = _add_spellblade_damage(state, rotation, autos, on_hits) _add_burn_damage(state, rotation) _add_item_proc_damage(state) _apply_damage_amplifiers(state, rotation) # fight-wide amps, applied last return {"breakdown": state.breakdown, "total_damage": state.total_damage, …}

Ordering here is load-bearing rather than stylistic. Buffs mutate stats before damage reads them; on-hits layer onto autos that have already been simulated; amplifiers apply to totals rather than to each source. Each step appends labelled rows to a shared breakdown, which is what the UI renders and what the golden snapshot locks.

Where the tricky bits live

  • Timing has one home. "When does a stack land" is answered by StackTimeline, built once per fight from the cast plan. Stacking DoTs, stack-triggered buff windows (Darius' Noxian Might), and per-cast stack counts all read that one object rather than each re-deriving cadence.
  • Mid-fight stat changes are handled as derivatives. A DamagePart carries bonus_ad_ratio — the part's derivative in bonus AD — so a steroid that lands mid-rotation reprices later casts correctly instead of the whole fight being computed at one stat snapshot.
  • Two fight modes. One-rotation (each ability once — burst) and time-based (abilities recast as cooldowns expire, autos woven in at a configured uptime — sustained). Ability haste is read as a champion stat like any other, through effective_cd = base_cd × 100 / (100 + haste).
  • Display text is minted here. Breakdown labels pass through the Flask layer and the frontend untouched, so there is no second place where a row can be described differently.
05

How champions are modelled

A champion is a slot map: {slot_key: slot_parser}, where a slot parser is a plain function SlotCtx → entry | None. There is no second parse path — the 31 champions with modules and the 142 without run the identical engine, differing only in which slot map it is handed.

Phase order

Slots are evaluated phase by phase, not in Q-W-E-R order. This is what makes cross-slot interactions work without any module coordinating with another:

BUFFMutates the shared stats context — R steroids, form changes.
DEBUFFMutates the target — resist shreds.
DAMAGEEmits castable entries. The default phase.
ONHITEmits effects layered onto autos.
AMPScales entries already computed.

Because BUFF runs first, a damage slot is guaranteed to read post-buff stats — an engine guarantee rather than a comment each module has to honor. Aatrox's R bonus AD is applied before his Q is priced, and neither slot function mentions the other.

Adding a champion: three tiers, cheapest first

  1. 1
    Nothing — the generic path

    Champions absent from the registry run GENERIC_SLOTS: classifier-driven damage detection on Q/W/E/R and on-hit auto-detection on the passive. It infers the damage type from the ability JSON and picks the leveling entry that best looks like primary damage. Free, and it covers 142 champions today.

  2. 2
    A slot map of archetypes

    The classifier guessed wrong, or the kit matches an existing shape (stat-buff ultimate, option-dispatched Q, %maxHP on-hit, toggle DoT). A new file that is mostly slotlib factory calls, plus one registry line. Ahri's E is this: simple_damage(dmg_type="magic") — generic apart from pinning the type.

  3. 3
    Custom slot functions

    Genuinely unique mechanics — multi-part output shapes, prose-regex values, cross-slot dependencies. Still a slot map; the custom function just sits beside the archetype calls. Ahri's W is one: three flames at two damage tiers, emitted as two DamageParts so each flame mitigates separately.

Trust boundary

Generic-path output is an estimate, never a cited number. The record so far is unambiguous: every champion anyone has actually sat down and analyzed has needed a module. Aurora's generic parse misread her passive's monster damage cap as a flat 200 on-hit and missed the Q recast entirely. Start at tier 1 anyway — verifying what generic already gets right is what scopes the module down to the parts that genuinely need custom handling.

The contract between layers

ability_spec.py is a dependency-free leaf that both the champion layer and the fight engine import, and which imports neither. A DamagePart carries the amount and count per mitigation unit, plus the handful of fields a timeline mechanic needs. Champion modules put all ability arithmetic there; the engine evaluates parts generically.

That boundary is enforced, not merely documented: every key an emitted entry may carry is whitelisted, and an unknown key raises at parse time. A typo like mr_reduction_flatt would otherwise silently shred nothing and quietly understate a champion forever. The same instinct as the item-value rule — the cheapest bug to fix is the one that refuses to run.

06

Verification

Patch resilience is only worth anything if we can tell when it fails. Three gates, with genuinely different jobs:

GateCatches
pytest 1,679 tests Hand-validated expected values per champion and per item, plus engine-core and generic-path roster coverage. Test layout mirrors source, so a champion module and its test are one filename apart.
pylint src/ Gates any code change.
golden_snapshot.py compare The one with non-obvious semantics. Locks whole-pipeline numeric output — every champion, both fight modes, a per-item sweep — to two decimals. A refactor must show zero diffs. A behavior fix re-captures the baseline with every diff explained in the commit.

The golden snapshot is what makes patch day tractable. Re-pulling data changes numbers by design, so a green test suite alone proves nothing; the snapshot turns "did anything else move?" into a diff you read in a minute, and a champion that moved without a patch note is the signal that a parse quietly broke.

07

Known limits

These are deliberate, and worth knowing before trusting an edge case:

  • Four castable slots. Multi-kit champions — Aphelios' weapons, Hwei's subspells, transformers — parse correctly, but the rotation engine and cast-order validation assume Q/W/E/R. A future workstream.
  • Half-parsed gimmick scalings. A handful of abilities come back from the wiki with values intact but units empty, so the generic path cannot attribute them — Aurelion Sol's Stardust stacks, Bard's Chimes, K'Sante's W resistances, Zeri's execute range, among others. Each needs a champion module for its stack mechanic regardless, so the parse fix belongs to that work rather than to patch day.
  • Gnar's Mega form. The worst case — its wiki leveling data is entirely empty, so the Mega stat bonuses live as tested constants. On a patch update those are verified against the game files (Community Dragon gnarbig.bin.json minus gnar.bin.json), not the wiki, whose Mega stat box has shipped wrong before.
  • Vendored scraper. vendor/lolstaticdata/ is external code. Minimal targeted fixes when a parser crash blocks a champion; no refactoring.
